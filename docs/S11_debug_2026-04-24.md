## 4. 발견된 버그 요약

### 버그 #1 — `upgrade_network_fail` 경로의 트랜시버/localDescription 롤백 누락 (수정 완료)

**위치**: [lib/services/call/webrtc_service.dart#L937-L994](../lib/services/call/webrtc_service.dart#L937-L994)

**현상**:
- `upgradeToCall()` 이 트랜시버 `SendRecv` 교체 + `createOffer()` + `setLocalDescription()` 까지 수행한 **후** `requestUpgrade` 의 NetworkException 을 만남
- catch 블록은 `FSM → connected` 로 되돌리기만 함
- PC 상태는 업그레이드된 상태 그대로 (SendRecv 트랜시버, upgrade 용 localDescription)

**결과**:
- 이후 발생하는 ICE restart 의 `restartIce() + createOffer()` 가 **업그레이드된 SDP 기반 offer** 를 생성 → Senior 에 "원격 비디오 트랙 수신" 이벤트 발생 (17:07:55.823 Senior 로그)
- Senior 는 monitor 경로 answer (SendOnly) 로 응답 → Family SendRecv ↔ Senior SendOnly **transceiver direction mismatch** 존재
- **본 S11 케이스의 17:08:07 Senior DISCONNECTED 는 direction mismatch 가 아니라 KEP WiFi drop (HW 이슈) 이 원인** (초기 분석 정정 — Senior 로그 필터에서 `NetworkMonitor`/`MtkConnectivity`/`WifiClient`/`wpa_supplicant` 누락으로 오판정했음)
- direction mismatch 자체의 실제 영향 범위는 미확정 — KEP WiFi drop 이 없는 환경에서 `upgrade_network_fail` 만 유발하여 Family 영상/음성의 Senior 측 전달 상태 재검증 필요
- 근본 문제는 "FSM connected 주장 vs PC SendRecv 업그레이드 상태" 의 **상태 불일치** 자체

**수정**: **옵션 B (즉시 hangUp) 채택** — [commit 예정]
- `webrtc_service.dart:L987-994` catch 블록을 `await hangUp(reason: TerminateReason.upgradeFailed)` 로 교체
- `monitoring_screen.dart:_handleTerminated` 의 `upgradeFailed` 경로에 `Navigator.pop` 추가 (PC 해제되므로 화면 유지 불가)
- `call_state_machine.dart:L38` UX 매핑 주석 업데이트
- 이유: 옵션 A (트랜시버 롤백) 는 flutter_webrtc v1.3.1 의 SDP rollback 지원 불명확 + 연쇄 await race 리스크로 HIGH 리스크. 옵션 C (자동 재시도) 는 트랜시버 롤백 미해결 + Senior incoming timeout 경합으로 HIGH. 옵션 B 가 MEDIUM 리스크로 가장 안전.

### 관찰 #2 — `upgradeToCall` 의 sequential await 제어 흐름 (독립 버그 아님)

**실제 동작 분석** (사용자 지적 + `writeOrTimeout` 코드 재확인):

`writeOrTimeout` ([network_guard.dart:27-45](../lib/services/network_guard.dart#L27-L45)) 는 모든 RTDB write 경로에서 일관되게 사용되며, `onTimeoutCleanup` 은 **`createCall` 에만** 설정됨 ([signaling_service.dart:208](../lib/services/call/signaling_service.dart#L208)). `sendRenegotiateOffer` / `sendIceRestartOffer` / `requestUpgrade` / `endCall` 은 `onTimeoutCleanup` 없이 단순 `op().timeout(timeout)` 으로 로컬 타임아웃만 체크하고 NetworkException throw.

→ 즉 offline 시 set 은 Firebase persistence 에 큐잉된 채 남고, 복구 시 flush 되어 Senior 에 도달. 초기 주장 "cleanup race 로 노드 삭제" 는 실제 코드 동작과 다름.

**Senior 가 renegotiateOffer 를 못 받은 실제 이유**:

[webrtc_service.dart:979-994](../lib/services/call/webrtc_service.dart#L979-L994) 의 sequential await 흐름:

```dart
try {
  await _signaling.requestUpgrade(cid);       // ← NetworkException 여기서
  await _signaling.sendRenegotiateOffer(...); // ← 도달 안 함 (스킵)
} on NetworkException { ... return; }
```

`requestUpgrade` 가 NetworkException 던지면 catch 로 점프. `sendRenegotiateOffer` **호출 자체가 안 됨** → set 큐잉도 안 됨 → Senior 에 영원히 도달 못함.

Senior 가 `upgradeRequest="call"` 을 받은 이유 (17:07:55.570): `requestUpgrade` 의 `set()` 은 throw 이전에 이미 로컬 큐에 들어갔음. Wi-Fi 복구 시 flush 되어 Senior 에 도달.

**결론**: 독립 버그 아님. "탭 안먹힘" 사용자 체감은 이 제어 흐름으로 인한 부작용. 버그 #1-B (즉시 hangUp) 로 수정하면 upgrade 자체를 포기하므로 이 관찰도 자동 해소.

### 버그 #3 (재정의) — Senior RESTARTING 상태에서 `status="ended"` 처리 지연

**재정의 근거**: 정상 hangUp 은 즉시 Senior 에서 stopPeer 됨. 이번 15s 지연은 KEP WiFi drop 이 선행되어 Senior 가 RESTARTING 상태였기 때문.

**실제 경로**:
1. 17:08:07 Senior WiFi drop → PC DISCONNECTED → FSM CONNECTED → RESTARTING → STOP_DELAY 15s 예약 (만료 예정 17:08:22)
2. 17:08:11 Family userHangup → `status="ended"` write
3. Senior `listenForCallEnd` 가 감지. 하지만 **"RESTARTING 중이므로 STOP_DELAY 타이머에 위임"** 설계 (17:07:55.019 Senior 로그에 동일 패턴 확인) 로 즉시 처리 스킵
4. 17:08:16 CallActivity post-accept timeout (17:08:01 수락 + 15s) 먼저 발동 → 종료
5. STOP_DELAY 자체는 17:08:22 만료 예정이었음

**판정 보류 — Senior 세션 핸드오버**:

이 설계 (RESTARTING 중 `status="ended"` 위임) 가 의도된 safety grace 인지, 실제 종결 의사는 즉시 반영해야 하는지는 Senior 측에서 판단할 사안. [`docs/S11_senior_handover.md`](S11_senior_handover.md) 에 맥락/증거/옵션 정리하여 Senior 세션에서 결정.

## 5. 본 회차 결론

- **S11 정규 시나리오 재현 실패** — Wi-Fi off 타이밍이 너무 빨라 `requestUpgrade` 단계에서 터짐. 다음 회차에는 탭 후 **1.5~2초 뒤** Wi-Fi off 로 조정.

- **노출된 이슈 재분류**:
  - **버그 #1** (트랜시버 롤백): 실제 버그. 옵션 B (즉시 hangUp) 로 수정 완료.

  - **버그 #3** (Senior RESTARTING 시 `status="ended"` 위임): Senior 세션에서 판단. `docs/S11_senior_handover.md` 로 전달.
- **사용자 체감 "탭 안먹힘"** 은 탭은 정상 ACCEPTED 됐으나 renegotiate 경로가 관찰 #2 로 깨진 것이 원인. 얼굴감지 자동수락이 안 된 원인은 별도 재검증 필요 (direction mismatch 와 WiFi drop 이 겹쳐서 분리 미확정).
